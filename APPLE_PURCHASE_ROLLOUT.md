## What Exists

- Apple's official Node App Store Server Library 3.1.0 verifies signed transactions and V2 notifications against the bundled Apple Root CA G3. Online certificate checks are enabled. `apple-root-g3.pem` came from https://www.apple.com/certificateauthority/AppleRootCA-G3.cer, not a client-supplied certificate.
- Every delivery verifies the submitted JWS, requests fresh transaction state from Apple's Get Transaction Info API, and verifies the returned JWS. Wrong app, environment, product, ownership, quantity, identity and date combinations fail closed. Xcode-local signed transactions are not accepted as App Store purchases.
- Firebase derives all four coin-pack amounts and nine ranked-pass mappings from a server allowlist, checked against an export of the actual Swift catalog. Client coin amounts and product names are not authority.
- `prepareWalletPurchase` binds the migration-generated appAccountToken to the Firebase UID before opening payment. Both purchase types send this token to StoreKit. The signed token and global transaction record prevent crediting the same purchase to another account.
- `claimWalletPurchase` atomically updates the shared ledger, mirrored balance and immutable receipt. Coin identity is the Apple transaction ID; non-consumable entitlement identity is its original transaction ID, scoped to the configured Apple environment. Repeated delivery returns current state without another grant.
- Coin and ranked purchases finish only after durable delivery succeeds. Account-bound unfinished transactions, ranked current entitlements and Transaction.updates provide retry/restore paths. User-initiated Restore Purchases invokes AppStore.sync; routine login does not prompt for it.
- `applePurchaseNotifications` verifies Apple's outer and inner signatures and retrieves fresh state. Refunds/revocations/reversals reconcile against the transaction's last accepted signed date. Duplicate or stale callbacks cannot repeat a grant. Unknown bindings fail for retry/support review rather than silently losing a refund.

## Refund Policy

Refunded coin grants are removed from the available balance, never making it negative. Any shortfall is recorded privately as `purchaseRefundDebt`. All future positive shared-ledger credits offset that debt before increasing available coins. Receipts contain grossDelta, refundDebtRecovered and the net delta. A refund reversal cancels the remaining adjustment and restores coins already recovered, idempotently.

The Shop shows an outstanding adjustment notice. New coin purchases are blocked before payment while a shortfall is present, so players are not charged for an unexpectedly reduced pack. Existing pending deliveries still reconcile normally. Gameplay grants may show a gross reward while the receipt/balance reflects the net recovery; broader result-screen refund detail remains a UI acceptance item.

Ranked refunds remove only the corresponding Apple grant. Other verified grants and separately reviewed migration baseline rights remain intact, along with daily entries/ad-ticket counters. The baseline is not proof of historical Apple ownership: review and reconcile it before launch, particularly any beta tester all-access flags. Do not use a baseline flag to mask a refunded historical entitlement.

## Operational Boundaries

- No production keys, flags, data, functions, rules or production App Store Connect settings were changed. Only the Sandbox notification URL was configured by the user. Test-project rules were subsequently updated to the dedicated purchase-only rules above; this does not deploy the full application's rules or enable its economy.
- Legacy transactions predating wallet migration and transactions lacking the exact server account token are rejected for review. There is no automatic historical rebinding/backfill tool yet. Blindly replaying old consumables could double-credit the opening balance.
- Keep purchase notifications active when pausing new purchases. Paused or failed notifications return 503 for Apple's retries. Apple's retries are finite: before launch add alerting and a notification-history reconciliation/support process for prolonged outages, unknown bindings and legacy refunds. This pass does not implement that operational worker.
- App Check enforcement, endpoint throttling, account-deletion handling and the rest of the economy migration are still release blockers. Test rules in an emulator and use actual Firestore transactions before rollout; the in-memory test double is not an emulator.
- Consumption requests are not automatically answered with user consumption data; no new consent or refund-contestation policy is introduced here.
- Do not enable the entire economy just because these endpoints compile. Friends/party daily play, Daily challenge grants and earned reward authority still need trusted migration.
